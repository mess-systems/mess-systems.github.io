**Лид:** Для Postgres в Kubernetes мы берём CloudNativePG. Continuous backup в object store из коробки есть. Шифрование объектов «как хочется» — не до конца. Ниже коротко: чем пользуемся, чего хотим, что уже есть и что ещё сделать.

## Чем пользуемся

Целевой стек для PostgreSQL у mess.systems — [CloudNativePG](https://cloudnative-pg.io/). На серверах mess.systems опираемся на него везде, где нужен Postgres в Kubernetes.

Оператор умеет непрерывный физический бэкап и архив WAL в object store через Barman Cloud (с 1.26 эта часть уходит в Barman Cloud Plugin — смысл тот же): base backup плюс поток WAL, из этого можно делать Point-in-Time Recovery.

## Что хотим

1. Бэкап пишется сам, без окна обслуживания и без ручного дампа.
2. Объекты в бакете в покое нельзя прочитать одним только доступом к бакету.
3. Ключ, которым кластер пишет в бакет, не совпадает с ключом расшифровки и не лежит рядом с секретами приложения.
4. Restore хотя бы раз пробовали, а не только описали.

Без пункта 2 бакет с base backup и WAL — это ещё одна копия боевых данных, только снаружи кластера. TLS тут не спасает: он закрывает канал, не объект на диске хранилища. Сжатие (`gzip`) тоже не шифрование.

## Что есть из коробки

В манифесте CNPG / Barman Cloud для `wal` и `data` есть поле `encryption`. Значения по сути: пусто (взять политику бакета), `AES256`, `aws:kms`.

Это **server-side encryption**: barman-cloud просит object store зашифровать объект при сохранении. Сжатие и шифрование настраиваются отдельно для WAL и для base backup. С `aws:kms` ключами можно управлять не тем же access key, которым пишут объекты.

Чего **нет**: client-side encryption — когда файл шифруется до выхода с ноды, а в бакет уходит уже нечитаемый blob. В barman-cloud этого пока нет; запросы открыты. Если хранилище не понимает `AES256` / `aws:kms` так, как ждёт barman-cloud, одна галочка в манифесте проблему не закроет.

Volume snapshots — отдельный контур (CSI / диск). Их retention и шифрование живут не в тех же полях `wal` / `data`.

## Что сделать, чтобы добиться желаемого

1. Явно задать `encryption` для `wal` и `data` (`AES256` или `aws:kms`), не надеяться на «у бакета вроде включено».
2. Проверить, что ваш object store реально принимает эти значения так, как их передаёт barman-cloud.
3. Развести права: write в бакет у кластера; decrypt / KMS — отдельно; bucket policy и object lock / versioning — не под одним только кластерным ключом.
4. Restore проверить отдельным контуром, лучше не теми же write-ключами, что у боевого кластера.
5. Отдельно решить шифрование для volume snapshots, если ими пользуетесь.

Ключи бэкапа и бакет с копиями не должны жить в одном контуре с тем, кто крутит кластер — иначе при потере секретов теряется и способ читать копии, и сами копии оказываются рядом.

## Что пока не понятно

Где для серверов mess.systems проходит граница: хватает server-side на доверенном своём object store, или нужен client-side / внешний encrypting proxy, потому что провайдер хранилища не в доверенной зоне. Это пока не понятно — это уже модель угроз для самого хранилища, а не настройка оператора Postgres.

Пока держим так: если ScheduledBackup зелёный, а `encryption` и разведение ключей не собраны — для нас это ещё не готовый бэкап, а удобная выгрузка.
