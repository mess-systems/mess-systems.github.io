Требования обычно живут отдельно от кода: в вики, в таблице, в системе задач. Пока команда маленькая и всё помнит, это работает. Потом начинаются вопросы, на которые трудно ответить: какое требование реализовано, где именно, есть ли на него тест, кто и когда поменял формулировку.

Когда к работе подключаются AI-агенты, вопросов становится больше. Агент быстро пишет код, но ему нужно понимать, какое требование он закрывает, и нельзя, чтобы он сам решал, что требование выполнено.

Мы опубликовали шаблон [mess-systems/requirements](https://github.com/mess-systems/requirements), в котором требования ведутся так же, как код. Ниже о том, как он устроен и почему именно так. Примеры в нём написаны для выдуманного продукта `x` компании mess.systems.

## Одно требование, один файл

Каждое требование это Markdown-файл с YAML-шапкой. Имя файла совпадает с ID, например `X-OPS-001.md`, а каталог совпадает с областью: `requirements/x-platform/`. В шапке тип, статус, приоритет, владелец, источник, связи с ADR и версия. Владелец это роль, например `role-platform-engineers`, а не фамилия.

В теле три обязательные части: само требование, обоснование и критерии приёмки. Требование без критериев приёмки не проходит проверку. Так формулировка «система должна быть надёжной» не попадёт в реестр: её придётся превратить в то, что можно проверить.

Почему файлы, а не таблица. У файла в git есть история, ревью через PR и автор каждой правки. Требование можно обсудить в том же месте, где обсуждают код, и изменить вместе с кодом в одном PR.

## Правила в конфиге, а не в скриптах

Префиксы ID, типы требований, области, статусы и приоритеты задаются в одном файле, `reqs.config.yaml`. Скрипты не знают ни одного ID заранее. Чтобы взять шаблон под свой проект, нужно поменять конфиг, а не код.

Проверку делает `validate.py`: схема шапки (`schema/requirement.schema.json`), совпадение имени файла и ID, префикс, тип, каталог, дубликаты, наличие критериев приёмки и маркера трассировки, существование ADR, на которые ссылается требование. Реестр собирает `generate.py`: из файлов получаются `REGISTER.md` и `register.json`. Руками реестр не правится, а CI проверяет, что он актуален.

## Строгость включается постепенно

Новое правило проверки нельзя включить сразу в режиме ошибки: оно сломает основную ветку на старых файлах. Поэтому у каждого правила свой режим. Сначала правило работает в режиме `warn`: CI печатает нарушения и прикладывает отчёт, но не падает. Потом отдельный PR исправляет файлы по отчёту. Когда отчёт пуст, правило переключается в `error` маленьким PR.

CI написан для GitHub Actions и для Forgejo Actions. Для простого случая всё сводится к одной команде: `make check`.

## Статусы ставит человек

Жизненный цикл требования: `draft`, `proposed`, `approved`, `implemented`, `verified`, и из любого статуса можно перейти в `deprecated`. Файл при этом не удаляется.

Главное правило: статусы `approved` и `verified` ставит человек через одобренный PR. Агент может создать черновик, предложить формулировку, связать требование с ADR, разметить код. Но решить, что требование утверждено или выполнено, он не может. Это записано и в процессе, и в инструкциях для агентов.

## Трассировка до кода и тестов

Для трассировки используется [OpenFastTrace](https://github.com/mess-systems/tech-radar/blob/main/technologies/openfasttrace.md). В требовании стоит маркер `req~X-OPS-001~1` и строка `Needs: impl, itest`, то есть требование ждёт реализацию и интеграционный тест. В коде реализации ставится тег `[impl->req~X-OPS-001~1]`, в тесте `[itest->req~X-OPS-001~1]`.

`make trace` собирает отчёт: какие требования покрыты кодом и тестами, а какие нет. Цифра в конце маркера это версия. Если формулировку утверждённого требования существенно поменяли, версия растёт, и трассировка покажет, что старые теги в коде нужно пересмотреть. По умолчанию отчёт не валит сборку, потому что примеры покрывают только часть требований. С `TRACE_STRICT=1` любой дефект трассировки становится ошибкой.

В шаблоне есть пример репозитория реализации с такими тегами, чтобы было видно, как это выглядит на практике.

## Решения рядом с требованиями

Требование отвечает на вопрос «что нужно», ADR на вопрос «почему решили так». В шаблоне есть шаблон ADR и два примера: про секреты и про резервное копирование. Связь двусторонняя: в требовании поле `links.adr`, в ADR список связанных требований. Валидатор проверяет, что ADR, на которые ссылается требование, существуют.

## Сайт для тех, кто не читает git

`make site` собирает сайт на [MkDocs](https://github.com/mess-systems/tech-radar/blob/main/technologies/mkdocs.md) из требований, реестра, ADR и описания процессов. Сборка идёт в строгом режиме, поэтому битая ссылка ломает её. Сайт нужен тем, кто читает требования, но не работает с git.

## Правила для агентов

Агенты работают по тем же правилам, что люди. В шаблоне есть `AGENTS.md` для любых агентов, правила для Cursor в `.cursor/rules/` и восемь готовых промптов: создать требование, связать с ADR, разметить код, проверить изменения, проверить покрытие, развернуть шаблон в новом проекте, исправить нарушения по отчёту, написать критерии приёмки.

Ограничения для агентов короткие: не повышать статусы, не обходить красный CI, проверять свободный номер ID перед PR, не удалять требования, а переводить в `deprecated`, и не вносить секреты, персональные данные и внутренние адреса.

## Как это связано с остальным

Имена продуктов, доменов, окружений и владельцев в требованиях берутся из [стандарта именования](https://github.com/mess-systems/naming-standard). Инструменты шаблона (OpenFastTrace, MkDocs, GitHub Actions, Forgejo Actions) описаны в [технологическом радаре](https://github.com/mess-systems/tech-radar). OpenFastTrace и MkDocs там в кольце trial: мы их пробуем, но ещё не считаем выбором по умолчанию. Требования к типовым архитектурам из [blueprints](https://github.com/mess-systems/blueprints) можно вести этим же шаблоном.

## С чего начать

Репозиторий отмечен на GitHub как шаблон: можно создать из него свой и пройти короткий quick start в README. Поменять префикс и области в конфиге, запустить `make check`, заменить примеры своими требованиями, оставить нужный CI и включить защиту ветки.

Чего я пока не знаю: как этот подход поведёт себя на сотнях требований и нескольких командах, где у каждой свой ритм. Шаблон распространяется под CC BY 4.0 для текстов и Apache-2.0 для кода. Если попробуете его у себя, [расскажите](/ru/about/), где он мешал.
